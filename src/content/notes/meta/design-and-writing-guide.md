## 1. 基本原则

文章优先保证信息清晰和阅读密度，不通过连续空行、整段粗体或复杂 HTML 制造视觉效果。

统一遵循：

- 只使用标准 Markdown；
- 页面标题来自 Frontmatter，正文不再写 H1；
- 正文从 H2 开始；
- 标题层级不跳级；
- 一个段落只表达一个主要观点；
- 代码、表格和引用只在真正有助于理解时使用；
- 不在 Markdown 中写颜色、字号和布局样式。

## 2. 标题

正文使用 H2、H3、H4：

```markdown
## 核心原理

### 数据流

#### KV Cache 更新
```

规则：

- H2 表示文章的主要章节；
- H3 表示 H2 下的子问题；
- H4 只用于必须进一步拆分的细节；
- 不要从 H2 直接跳到 H4；
- 标题应描述问题，不使用“其他”“补充”等模糊名称；
- 标题不手写编号之外的装饰符号。

左侧“本文目录”会自动展示 H2、H3、H4。

## 3. 段落

一个段落建议控制在 2–5 行。观点变化时再换段，不要每句话都换行。

推荐：

```markdown
Prefill 一次处理全部输入 Token，通常更受计算能力影响。
Decode 每轮只生成一个 Token，需要反复读取模型权重，因此更容易受显存带宽限制。
```

不推荐：

```markdown
Prefill 一次处理全部输入 Token。

通常更受计算能力影响。

Decode 每轮只生成一个 Token。
```

不要使用多个空行增加间距，页面样式会自动处理段落间隔。

## 4. 粗体

粗体只强调关键词或短结论：

```markdown
MTP 的核心是**同时预测多个未来 Token**。
```

避免整段加粗：

```markdown
**关键点：第 ④⑤ 步会对每个位置都计算一遍，这意味着所有内容都非常重要。**
```

更好的写法：

```markdown
关键点：第 ④⑤ 步会对**每个位置**都计算一遍。
```

整段粗体会降低层次感，并让中文字体显得过重。

## 5. 列表

列表适合表达：

- 并列条件；
- 操作步骤；
- 优缺点；
- 检查清单；
- 参数含义。

列表项尽量保持语法一致：

```markdown
- 降低 KV Cache 占用；
- 减少显存带宽读取；
- 提升 Batch 容量。
```

不要将连续说明强行拆成列表：

```markdown
- 模型会先执行 Prefill。
- 然后模型开始 Decode。
- 最后返回结果。
```

这种情况使用普通段落更自然。

有严格顺序时使用有序列表：

```markdown
1. 加载模型；
2. 构造请求；
3. 执行 Benchmark；
4. 对比指标。
```

## 6. 行内代码

参数、变量、文件名和短表达式使用行内代码：

```markdown
设置 `num_speculative_tokens=4` 后，Verifier 最多检查 4 个 Draft Token。
```

适合行内代码的内容：

- `SamplingParams`
- `prompt_logprobs`
- `src/lib/papers.ts`
- `P(x) / Q(x)`

不要用行内代码强调普通中文词语。

## 7. 代码块

代码块必须注明语言：

````markdown
```python
from vllm import LLM

llm = LLM(model="Qwen/Qwen3-8B")
```
````

命令使用：

````markdown
```bash
npm run check
npm run build
```
````

数据流和 ASCII 图使用：

````markdown
```text
Request → Scheduler → ModelRunner → Sampler
```
````

代码块中只放代码或结构图，解释写在代码块外。

## 8. 表格

表格适合需要横向比较的内容：

- 参数差异；
- 指标对比；
- 字段说明；
- 修复前后行为；
- Shape 变化。

```markdown
| 参数 | 作用 | 默认值 |
|---|---|---|
| `temperature` | 控制随机性 | `1.0` |
| `top_p` | 核采样阈值 | `1.0` |
```

表格单元格保持简短。超过两三句话的说明应移到正文。

不要使用表格模拟页面布局。

## 9. 引用

引用块用于：

- 实验环境；
- 原文定义；
- 重要前提；
- 需要与正文区分的说明。

```markdown
> 本文数据来自 vLLM 0.24.x 的实际运行结果。
```

普通结论不需要放入引用块。

## 10. 分隔线

分隔线使用：

```markdown
---
```

只用于大段内容之间的语义分隔，不要在每个章节前后都添加。

标题本身已经提供视觉层级，通常不需要额外分隔线。

## 11. 链接

标准写法：

```markdown
[vLLM 官方文档](https://docs.vllm.ai/)
```

规则：

- 论文优先链接 arXiv `/abs/` 页面；
- 源码优先链接具体文件或 Commit；
- 链接文字说明目标内容，不使用“点击这里”；
- 外部结论注明来源；
- 不复制受版权保护的大段原文。

## 12. 图片

图片应包含有意义的说明：

```markdown
![vLLM 推理执行流程](./images/vllm-flow.png)
```

规则：

- 图片服务于数据流、架构或实验结果；
- 不使用纯装饰图片；
- 截图裁掉无关界面；
- 正文中解释图片的关键结论；
- 图片文件名使用小写英文和连字符。

## 13. 技术文章推荐结构

```markdown
## 问题与背景

## 基础概念

## 核心原理

## 数据流或执行过程

## 代码实现

## 实验与性能

## 限制

## 总结

## 参考资料
```

不要求每篇文章包含全部章节，但建议遵循“为什么 → 原理 → 实现 → 验证 → 限制”的顺序。

## 14. 论文解读推荐结构

```markdown
## 论文信息

## 一句话结论

## 研究动机

## 方法与公式

## 架构和数据流

## 实验设计

## 结果解读

## 与相关方案比较

## 工程实现

## 局限

## 我的理解

## 延伸阅读
```

论文解读不能只复述摘要，应说明：

- 方法为什么有效；
- 实验是否支持结论；
- 性能收益成立的条件；
- 与现有实现的差异；
- 论文没有覆盖的问题。

## 15. 发布前排版检查

- [ ] 正文没有重复 H1；
- [ ] H2/H3/H4 没有跳级；
- [ ] 没有整段滥用粗体；
- [ ] 没有连续空行；
- [ ] 列表项语法一致；
- [ ] 代码块注明语言；
- [ ] 表格内容足够简短；
- [ ] 引用块只用于前提或原文；
- [ ] 链接文字清楚；
- [ ] 图片有 Alt 文本；
- [ ] 没有内联颜色和自定义字号；
- [ ] 桌面和移动端没有横向溢出。
